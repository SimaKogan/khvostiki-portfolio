# Архитектурные решения

Короткие записи о том, **что выбрано и почему**.

## 1. Остаёмся на ванильном HTML/CSS/JS

Сайт состоит из семи страниц с небольшим количеством интерактива. Фреймворк и сборка добавили бы зависимости и сложность, не давая выгоды. Результат открывается как обычный набор файлов, а Lighthouse показывает 96–100 по производительности.

## 2. Бэкенд только там, где он нужен: заявка на усыновление

Раньше форма «готовила текст», который человек сам копировал и отправлял в Telegram. Это лишний шаг и потерянные заявки. Теперь заявка уходит на сервер и попадает волонтёрам в чат.

**Почему Vercel Function на Node.js, а не Express/Firebase/PHP-хостинг:**

| Вариант | Минусы |
|---|---|
| Свой сервер (Express на VPS) | платный, нужно администрировать |
| Firebase / Supabase | есть бесплатный тариф, но нужны база данных и правила доступа, а хранить в ней персональные данные не требуется |
| Сервисы форм (Formspree и т. п.) | лимиты и зависимость от стороннего сервиса, нечего показать как код |
| **Vercel Function + Telegram** | тариф Hobby бесплатный и без карты, нет сервера и базы, привычный Node.js без зависимостей, деплой при каждом push, заявки сразу в рабочем чате |

Ограничение: Hobby предназначен для личных некоммерческих проектов. Поэтому ядро API (`server/lib/handle.js`) написано на стандартных `Request`/`Response` и не привязано к платформе: оно переносится на Cloudflare Workers, Netlify или Deno Deploy заменой тонкого адаптера (`server/api/apply.js`).

Функция ничего не хранит: меньше риска утечки персональных данных.

**Лимит запросов.** Счётчик живёт в памяти экземпляра функции, поэтому защита приблизительная: она отсекает быстрые повторы и простых ботов. Основную защиту дают проверка Origin и скрытое поле-ловушка; для строгого лимита понадобилось бы общее хранилище. Это сознательный компромисс ради нулевых зависимостей и нулевой стоимости.

## 3. Прогрессивное улучшение: форма работает без бэкенда

Адрес API задаётся атрибутом `data-endpoint` у формы (на деплое подставляется из переменной `API_URL`). Если он пуст или сервер недоступен, форма показывает готовый текст заявки с кнопками «Открыть Telegram» и «Скопировать». Сайт остаётся рабочим на чистом GitHub Pages, а при сбое API никто не теряет заявку.

## 4. Видео вместо GIF в hero-баннере

GIF весил 2,2 МБ и грузился на каждой странице. WebM занимает ≈220 КБ, MP4 ≈430 КБ (запасной формат). Добавлены постер, `muted` + `playsinline` (для автоплея на iOS), кнопка паузы (WCAG 2.2.2) и остановка при `prefers-reduced-motion`.

## 5. Подстановка адресов при деплое, а не в коде

Мета-теги Open Graph, `canonical`, `sitemap.xml` и `robots.txt` требуют абсолютных URL. В исходниках стоит маркер `__SITE_URL__`, а workflow подставляет реальный адрес (`https://<логин>.github.io/<репозиторий>` или свой домен из переменной `SITE_URL`). Код не привязан к конкретному аккаунту, репозиторий можно форкнуть без правок.

## 6. Доступность как требование, а не украшение

- `<button>` с `aria-expanded` вместо скрытого чекбокса для мобильного меню (с клавиатуры чекбокс недоступен);
- `<main>`, skip-ссылка, `aria-current`, корректная иерархия заголовков;
- контраст кнопок и ссылок ≥ 4,5:1 (был 3:1);
- устаревшие атрибуты (`align`, `border`, `cellpadding`, `<nobr>`) заменены CSS.

## 7. Проверки в CI

На каждый push и pull request: валидация HTML, проверка внутренних ссылок и якорей, тесты API. Dependabot раз в месяц обновляет зависимости и версии actions.

## Что можно сделать дальше

- Вынести повторяющиеся шапку/подвал в шаблоны (например, Eleventy) и убрать дублирование между страницами.
- Хранить карточки питомцев в `pets.json` и строить их на клиенте или на этапе сборки.
- Конвертировать фотографии в WebP/AVIF и добавить `srcset`.
- Добавить Lighthouse CI в pull request.
